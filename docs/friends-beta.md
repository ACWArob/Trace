# Trace friends beta

The cloud HTTPS server must be reachable before preparing a connected phone build. The laptop is only a development machine. Friends use the hosted server for accounts, catalog searches, shared scores, and private library synchronization.

## Build both platforms against one server

From the repository root, with the existing local npm dependencies installed:

```sh
TRACE_NATIVE_API_ORIGIN=https://your-actual-trace-domain.example node scripts/prepare-release.mjs
```

Replace the example with the deployed origin. The command requires a successful `/api/health`, rejects missing/local/HTTP/development origins, builds the public bundle once, runs the locally installed Capacitor CLI, and checks that Android and iOS received the same connected configuration. It does not sign or upload a build. Keep provider keys on the server.

Use this command for a release candidate. `npm run native:sync` is the development command and rebuilds with its current environment. If the existing bundle is connected, omitting the origin now stops before overwriting it. Returning to an offline development bundle requires the explicit `TRACE_NATIVE_ALLOW_OFFLINE=1` environment switch; release builds reject that switch. Re-run release preparation after every interface change before creating a distributable archive. See [Capacitor sync](https://capacitorjs.com/docs/getting-started).

The server origin is pinned to an installation to protect queued private edits. Keep the same production origin for updates. Use another application identifier for staging. Sync or export pending edits before uninstalling an old debug app; a debug signature and a release signature cannot update each other.

## Android

Create the release signing key through Android Studio's **Generate Signed App Bundle or APK** flow, retain an encrypted backup, and keep it outside this checkout. A key is not generated by Trace's build scripts. Configure these environment variables privately without putting their values in shell history or chat:

- `TRACE_ANDROID_KEYSTORE` — absolute path to the private release keystore.
- `TRACE_ANDROID_STORE_PASSWORD` — keystore password.
- `TRACE_ANDROID_KEY_ALIAS` — signing alias.
- `TRACE_ANDROID_KEY_PASSWORD` — alias password.
- `TRACE_ANDROID_VERSION_CODE` — increasing positive build number; defaults to `1` for development.

With Java 21 and the Android SDK installed, build from `native/android`:

```sh
./gradlew assembleRelease
# For Google Play's testing track instead:
./gradlew bundleRelease
```

Release tasks fail when signing configuration is missing. Debug builds still use the existing debug configuration. Signed APK output is `native/android/app/build/outputs/apk/release/app-release.apk`; Play bundle output is `native/android/app/build/outputs/bundle/release/app-release.aab`. These outputs and signing files are ignored by Git. Verify the APK signature with Android SDK `apksigner verify --verbose` before distribution. Keep the signing key stable across APK updates. [Android signing guidance](https://developer.android.com/studio/publish/app-signing)

For a small friend group, choose a supported Android limited-distribution or Play testing route for the testers' devices and regions. Developer verification requirements can affect direct APK installation. Review [Android limited distribution](https://developer.android.com/developer-verification/guides/limited-distribution) before sending an APK.

## iPhone and TestFlight

1. Enroll in the Apple Developer Program and confirm ownership of the `com.acwarob.trace` identifier, or select an owned identifier consistently in Capacitor, Xcode, and App Store Connect.
2. Run the connected release-preparation command above. Open the iOS project with `npm run native:ios`.
3. In Xcode, select the owner development team and signing configuration. Set a release version and an unused increasing build number. Select a generic iOS device destination and use **Product → Archive**.
4. In Organizer, validate the archive and choose **Distribute App → App Store Connect**. Complete the real app's privacy, export-compliance, support, and beta-review information. Do not infer answers from the presence of a WebView.
5. After Apple processes the build, create an external TestFlight group, add the build, and submit it to TestFlight App Review. Invite friends only after the build is approved for external testing. Tester invitations are separate from Trace account invites.

The first external build requires Apple's beta review. Enrollment, signing access, processing, and review are external gates. An unsigned simulator build does not satisfy them. [Upload builds](https://developer.apple.com/help/app-store-connect/manage-builds/upload-builds/), [invite external testers](https://developer.apple.com/help/app-store-connect/test-a-beta-version/invite-external-testers/)

## Device acceptance checks

Use isolated beta accounts and test data first. Test these on a physical Android phone and iPhone against the same deployed server:

- Turn the laptop off and use mobile data. Sign in, search a regional title, add it, and restart Trace.
- Save a photo from the picker and camera; reopen it after restarting. Confirm another account cannot see it.
- Log a rating offline, close the app, reopen, reconnect, and confirm the edit reaches a second device without duplication.
- Test a conflicting edit from two devices and both conflict choices. Test expired sessions and sign-out/account switching.
- Import an export file, produce a Tracewall image, and share/save it through the phone's supported flow.
- Check the keyboard, safe areas, Android Back, external source links, and installation/update behavior.
- Install a subsequent signed build over the previous beta and confirm private data and pending edits survive.

Public home-screen installation is available through the hosted browser app while native distribution is pending: Android Chrome's install action or iPhone Safari's **Share → Add to Home Screen**. Validate cold offline launch on those physical browsers too.

## Current verification boundary

Android debug builds and iOS simulator builds were verified during development. The release-preparation helper has isolated configuration/health/copy checks. A signed release, production-connected physical-device run, TestFlight upload, and external review must each be recorded when actually completed. No publishing or account enrollment is performed by these scripts.
